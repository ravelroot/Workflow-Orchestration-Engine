Capítulo 1

Visão geral

O Delco é um motor de orquestração de workflows de código aberto, no estilo do Apache Airflow e do Temporal. Você descreve um pipeline em Python como um grafo de tarefas com dependências; o Delco agenda as execuções, distribui as tarefas entre workers, repete o que falhar com espera exponencial e mostra tudo em tempo real num painel web.

O diferencial de engenharia é a confiabilidade: o estado de cada execução vive no MySQL. Se o servidor cair no passo 23 de um fluxo de 50, ao voltar o Delco sabe exatamente onde parou e refaz só o passo 23.

Para que serve

Qualquer rotina com várias etapas que precisa rodar sozinha, no horário certo, sem perder o fio quando algo dá errado: ETL e relatórios, integrações com fornecedores instáveis, sincronizações, backups, migrações em lotes, processamento de arquivos e notificações.

O que o Delco faz

Para quem escreve workflows

  • Workflows como código Python, com dependências, agenda cron, fila, tempo limite e retentativas por tarefa.
  • Parâmetros tipados com Param: o painel monta o formulário e todos os caminhos validam do mesmo jeito.
  • ctx.skip(), ctx.fail() e retry_on para separar erros passageiros de definitivos.
  • Tempo limite da execução inteira com run_timeout.
  • delco new e delco dev run para criar e testar um workflow sem subir nada.

Para quem opera

  • Painel com grafo ao vivo, grade, linha do tempo, logs que chegam enquanto a tarefa roda e quadro de vagas dos workers.
  • Disparo com formulário, reprocessamento de períodos, retomada da falha, marcação manual de tarefas e ações em lote.
  • Pausa de agendas e de workers, tela Sistema, delco doctor, métricas para o Prometheus e healthchecks.
  • Avisos no Slack, Discord, Teams, Google Chat, Telegram, por e-mail e por webhook assinado.

Para quem administra

  • Três papéis (Leitura, Operador e Administrador), tokens pessoais com validade e auditoria com filtros e exportação.
  • Configuração conferida ao subir, limites de chamadas e limpeza automática do histórico.

Capítulo 2

Como rodar

Requisitos

  • Docker com Docker Compose (Docker Desktop no Windows ou no macOS).
  • Cerca de 1,5 GB livres para as imagens e a porta 8080 livre (troque com DELCO_PORT).

Primeira execução

  1. Baixe o repositório (Code → Download ZIP no GitHub ou git clone).
  2. Windows: dois cliques em iniciar.cmd. Linux ou macOS: ./iniciar.sh (ou make subir).
  3. Na primeira vez o script cria o .env com senha do MySQL, chave secreta e token de métricas aleatórios.
  4. O Docker sobe MySQL, Redis, API, agendador e dois workers, e o painel abre em http://localhost:8080.
  5. Confira tudo com docker compose exec api delco doctor.
cp .env.example .env              # troque DELCO_DB_PASSWORD e DELCO_SECRET_KEY
docker compose up -d --build
docker compose up -d --scale worker=4
docker compose exec api delco doctor

Capítulo 3

Escrevendo workflows

Estrutura de um arquivo

Cada arquivo .py da pasta workflows/ (ou de DELCO_WORKFLOWS_DIR) define um ou mais objetos Workflow. O agendador relê a pasta a cada 30 segundos; arquivos começando com _ são ignorados. O jeito mais rápido de começar é delco new nome --schedule "0 7 * * *", que cria o arquivo já com parâmetros e duas tarefas.

from delco import Fail, Param, Workflow

vendas = Workflow(
    "relatorio_vendas",
    description="Extrai, agrega e publica o relatório do dia.",
    schedule="0 7 * * *",
    timezone="America/Sao_Paulo",
    params={
        "dias": Param(1, min=1, max=30, description="Quantos dias processar"),
        "formato": Param("csv", choices=["csv", "xlsx"]),
    },
    run_timeout=1800,
)

@vendas.task(retries=3, timeout=120, retry_on=(ConnectionError, TimeoutError))
def extrair(ctx):
    linhas = buscar_pedidos(ctx.params["dias"])
    if not linhas:
        ctx.skip("Nenhum pedido no período")
    return {"linhas": len(linhas)}

@vendas.task(depends_on=[extrair])
def publicar(ctx):
    if ctx.upstream["extrair"]["linhas"] > 1_000_000:
        raise Fail("Volume fora do normal")
    ctx.log("publicado")

Para gerar tarefas em laço, use wf.add_task(nome, funcao, depends_on=[...]). Funções async def também funcionam.

Parâmetros tipados

Param declara o que cada parâmetro aceita. A mesma regra vale no formulário do painel, na API, na CLI, no gatilho por URL, no reprocessamento e no delco dev run. Erros voltam por campo: {"params.dias": "Precisa ser no máximo 30."}.

ArgumentoDescrição
primeiro argumentoValor padrão; sem ele, o parâmetro é obrigatório
typestr, int, float, bool, date, list ou dict (deduzido do padrão)
choicesLista de opções (vira um seletor no formulário)
min · maxLimites de números ou tamanho de textos e listas
description · labelAjuda e rótulo do campo
requiredForça obrigatório mesmo com padrão
secretMascara o valor no painel, na API e na auditoria

Textos vindos da CLI e de formulários são convertidos ("3" vira 3, "sim" vira True). Datas chegam à tarefa como "AAAA-MM-DD". Parâmetros declarados sem Param continuam livres, como nas versões anteriores. Um workflow agendado não pode ter parâmetro obrigatório sem padrão.

O objeto ctx, skip, fail e retry_on

Atributo ou métodoO que faz
ctx.paramsParâmetros já validados
ctx.upstreamResultado de cada dependência, por nome
ctx.log(msg, level) · ctx.warning · ctx.errorLinhas de log; print e o logging também viram log
ctx.progress(50, "metade")Barra de andamento no painel
ctx.skip("motivo") ou raise Skip(...)A tarefa termina como pulada; dependentes com all_success também são puladas e a execução conta como sucesso
ctx.fail("motivo") ou raise Fail(...)Falha definitiva, sem retentativas (retry=True para repetir)
ctx.idempotency_keyIgual em todas as tentativas: use para não repetir efeitos externos
ctx.logical_date · ctx.attempt · ctx.is_retry · ctx.is_last_attemptHorário agendado (ou do reprocessamento) e tentativa atual
Com retry_on=(ConnectionError, TimeoutError), uma queda de rede é repetida, mas um KeyError por erro de código falha na hora, sem esperar as retentativas. O log da tentativa avisa: “Erro marcado como definitivo”.

Testar sem servidor

delco dev run relatorio_vendas -p dias=3          # roda aqui, na ordem, com logs
delco dev run relatorio_vendas --no-retries --output
delco dev run relatorio_vendas --json            # para scripts
delco validate workflows                         # confere os arquivos

O delco dev run não precisa de MySQL, Redis nem workers: executa as tarefas no próprio processo, respeitando dependências, regras de disparo, skip, Fail e retentativas (sem a espera). Dentro dos seus testes, vendas.run_local({"dias": 3}) devolve o estado, as tentativas, os logs e o resultado de cada tarefa.

Versões

O Delco calcula uma impressão digital do grafo (tarefas, dependências e opções). Quando ela muda, nasce uma versão nova; cada execução guarda a versão com que começou. O código do arquivo também fica guardado e aparece na aba Código. Mudar só o corpo de uma função não cria versão.

Exemplos prontos: ola_delco, relatorio_vendas_diario (leque paralelo, parâmetros, skip, Fail e retry_on), sincronizar_catalogo, backup_noturno (fila critical e run_timeout) e migracao_em_50_passos.

Capítulo 4

Guia das telas

O painel tem uma barra lateral com Visão geral, Workflows, Execuções, Workers, Desempenho, Integrações, Sistema e a documentação da API. Ctrl K (ou ⌘K) abre a paleta de comandos e ? lista os atalhos. Se nenhum agendador estiver ativo, um aviso aparece no topo de todas as telas.

Entrada

Visão geral

O quadro Agora mostra cada worker e suas vagas, acesas quando uma tarefa está rodando (workers pausados aparecem com as vagas tracejadas). Abaixo, indicadores de 24 horas, tarefas por hora, próximas execuções e as execuções recentes.

Workflows

A lista mostra agenda, últimas execuções e taxa de sucesso. Marque vários para pausar ou retomar as agendas de uma vez.

Detalhe do workflow

Fatos (agenda, próxima execução, versão, arquivo, limites) e as abas Grade, Grafo, Tarefas e parâmetros, Execuções, Versões e Código. A aba aberta fica no endereço da página, para compartilhar o link.

Executar e reprocessar

Executar abre um formulário montado a partir dos parâmetros (ou um editor JSON, para quem prefere). Erros aparecem embaixo de cada campo. Reprocessar período (workflows com agenda) mostra quantos horários existem entre as datas, quais já têm execução e cria uma execução por horário, com a data lógica certa.

Execuções

Filtros por estado, workflow, origem (inclusive Reprocessamento) e período, busca por número ou observação e Exportar CSV. Marque execuções para cancelar, retomar da falha ou excluir (administrador) em lote. O tamanho da página segue a preferência da conta.

Execução

Grafo ao vivo, tarefas, linha do tempo e parâmetros. O motivo da falha da execução (como o tempo limite) aparece em destaque e a duração vem comparada com a mediana das execuções anteriores (“12% mais lenta”). A observação pode ser editada pelo lápis, e o administrador pode excluir uma execução terminada.

Gaveta da tarefa

Log ao vivo com busca, filtro por nível, acompanhar o fim, quebrar linhas, ir para o primeiro erro, copiar e baixar. Abas de resultado e tentativas, com traceback. Em execuções terminadas, o operador pode reexecutar a partir desta tarefa ou marcar como sucesso, falha ou pulada: marcar como sucesso devolve à fila as tarefas que tinham sido puladas por causa dela, e a execução continua.

Workers

Cada worker com suas vagas e o que está rodando, e as filas no MySQL e no Redis. Pausar faz o worker terminar o que está rodando e parar de pegar tarefas novas; Retomar o devolve ao trabalho.

Desempenho

Integrações

Sistema

Só para administradores. Resume a saúde (tudo certo, avisos ou problemas), mostra MySQL, Redis, agendadores e workers, lista as verificações com o que fazer em cada aviso, os agendadores com seu último sinal e erro, a configuração em uso (senhas mascaradas), o exemplo de configuração do Prometheus e o botão Rodar limpeza agora.

Minha conta, preferências e paletas

As preferências ficam na conta e valem em qualquer navegador: tema (sistema, claro ou escuro), paleta de cores, datas no horário local ou em UTC, densidade das tabelas, execuções por página, avisos do navegador (falhas e execuções que você disparou) e quebra de linha nos logs. A paleta tem cinco opções, escolhidas pelas amostras de cor:

Cada paleta tem versão clara e escura; a marca preta e branca do Delco não muda. A primeira é a paleta original do Delco.

Usuários e auditoria

Administradores criam e editam usuários e consultam a auditoria com filtros por ação, pessoa, período e busca, com paginação e exportação em CSV.

Paleta de comandos e atalhos

Ctrl K busca telas, workflows e execuções (#118) e executa ações: executar workflow, trocar tema, trocar a paleta de cores, preferências, pausar ou retomar todas as agendas. Atalhos: g v, g w, g e, g k, g d, g i, g c, g u, g s, / para buscar e x para executar.

Arquitetura

ProcessoComandoResponsabilidade
APIdelco apiDaphne com o Django: REST, WebSocket, painel, Swagger, métricas e migrações
Agendadordelco schedulerLê a pasta (e guarda o código), cria execuções agendadas, libera tarefas, encerra execuções que passaram do tempo limite, recupera leases vencidos, republica mensagens perdidas, envia notificações e manda sinal de vida ao Redis a cada 5 s
Workerdelco workerConsome as filas, assume cada tarefa no banco e roda a tentativa num processo filho com heartbeat, tempo limite e cancelamento; obedece a pausas

Ciclo de vida de uma tarefa

  1. O agendador marca a tarefa como na fila no MySQL e só depois publica no Redis.
  2. O worker trava a linha com select_for_update() e status='queued'; mensagem repetida não encontra mais a tarefa na fila.
  3. A cada heartbeat o worker renova o lease. Se o servidor cair, o lease vence e a tarefa volta para nova tentativa.
  4. O processo filho devolve resultado, erro (com a indicação se pode ser repetido) ou skip.
  5. Tarefas terminadas guardam o resultado e não rodam de novo: só o passo interrompido é refeito.

Confiabilidade e retomada

  • MySQL é a fonte da verdade; o Redis é só transporte.
  • Compare-and-set em toda transição; FOR UPDATE SKIP LOCKED deixa vários agendadores trabalharem juntos.
  • Chave única por horário impede duas execuções agendadas no mesmo horário.
  • Mensagens perdidas são republicadas; o Redis pode ser apagado sem perda.
  • Worker pausado devolve à fila mensagens que já tinha lido.
  • Tempo limite da execução: o agendador confere a cada ciclo de recuperação, cancela o que falta, pede parada ao que roda e grava o motivo.

Sinais de vida

Workers gravam o heartbeat no MySQL. Agendadores gravam um sinal com validade no Redis (delco:scheduler:<id>), com ciclos, última leitura da pasta e último erro. A API usa esse sinal na saúde, no aviso do painel e na tela Sistema. Cada processo também escreve um arquivo de saúde usado pelo delco healthcheck.

Gatilho por URL

A URL aparece uma única vez (só o SHA-256 do token fica no banco). Com Exigir assinatura, o Delco mostra também um segredo e recusa chamadas sem X-Delco-Signature ou X-Hub-Signature-256 (o formato dos webhooks do GitHub). Cada gatilho aceita até DELCO_HOOK_RATE_LIMIT chamadas por minuto.

BODY='{"params": {"pasta_saida": "/tmp/rel"}, "note": "Build 42"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$DELCO_HOOK_SECRET" | cut -d' ' -f2)
curl -X POST "$DELCO_HOOK_URL" -H 'Content-Type: application/json' \
  -H "X-Delco-Signature: sha256=$SIG" -d "$BODY"

E-mail

Configure DELCO_SMTP_HOST, DELCO_SMTP_PORT, DELCO_SMTP_USER, DELCO_SMTP_PASSWORD, DELCO_SMTP_FROM e DELCO_SMTP_SECURITY (starttls, ssl ou none). A mensagem sai em texto e HTML, com o link para a execução.

Capítulo 10

Operação em produção

Checklist

  • DELCO_ENVIRONMENT=production, DELCO_SEED=false, DELCO_SECRET_KEY longa, DELCO_ALLOWED_HOSTS e DELCO_PUBLIC_URL com o domínio real.
  • HTTPS num proxy reverso (Nginx, Caddy, Traefik) repassando X-Forwarded-Proto e o WebSocket em /api/ws.
  • Contas de demonstração desativadas ou com outra senha; delco doctor --strict sem avisos.
  • Backup diário do MySQL (o Redis pode ser perdido sem perda de dados).

Diagnóstico

docker compose exec api delco doctor
CONFIGURAÇÃO
  ✓ Chave secreta: Definida em DELCO_SECRET_KEY.
PROCESSOS
  ✓ Agendador: 1 ativo(s): api-1
  ! Filas sem worker: Nenhum worker online consome: relatorios
      → Inclua a fila em DELCO_WORKER_QUEUES de algum worker.

Um bom alerta: delco_schedulers == 0 por 2 minutos.

Healthchecks, escala e manutenção

  • O docker-compose.yml usa delco healthcheck na API, no agendador e nos workers.
  • Escale workers com --scale worker=N e separe filas pesadas com DELCO_WORKER_QUEUES.
  • Antes de mexer numa máquina, pause o worker pelo painel ou com delco workers pause id.
  • Atualizações: git pull e docker compose up -d --build; a API aplica as migrações com trava.
  • Logs em JSON com DELCO_LOG_FORMAT=json, prontos para Loki, Elastic ou Datadog.
